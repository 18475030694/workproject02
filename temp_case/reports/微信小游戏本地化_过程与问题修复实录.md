## 2. 卡点①：登录死循环（VERIFY / 反复回登录页）

- **现象**：DevTools 里登录被判定为「审核版」，强制路由到关闭的审核服，死循环。
- **排查**：版本链三层核对——`buildVersion`（必须三段式，否则 hotupdate/res_version 校验死循环）、包内 `Version.ts` 常量（1.0.0 被服务端判审核版）、plat 后台配置。
- **根因（两个叠加）**：
  1. 包内写死 `Version = "1.0.0"` 被判审核版；
  2. **plat 后台 `platadmin_config.audit_version` 配置含 "1.0.0"**，即使版本改对仍被拦 → 同时影响网页端和微信端。
- **修复**：`buildVersion` 前两段改 2.0.0 跳出死循环（第三段 0 不影响 res_version.0.json）；DB 直改 `192.168.*.*:3306 root/*** 库=game_dev` 的 `platadmin_config.audit_version` → `[]`，调 `update_configs` 刷新内存配置，`/default_config` 验证返回空。脚本 `fix_plat_audit_version.py`（只读，--apply 带备份）。
- **教训**：微信端 version 重写 hook（game.js PLAT-CFG-PATCH）治标，plat 配置才是本；audit 清空后 hook 保留无害。

## 3. 卡点②：战斗崩溃 `createEngine:fail create time_limit`（10-26）

- **现象**：主城能进，进战斗必挂。
- **弯路**：先怀疑 iOSHighPerformance 高性能模式（game.json 摘除后依旧，排除）；一度误判为 DevTools 工具层问题（后推翻）。
- **根因**：`MultTextures.ts`（多纹理合批）在 `EVENT_GAME_INITED` 无条件 `loadBundle('multTextures')`；settings 把它配成**微信分包** → 走 `wx.loadSubpackage` → DevTools 为分包创建引擎上下文超时。启动失败被 `bundle &&` 静默吞掉（所以主城没事），战斗时渲染重试 → 未捕获异常 → HyperError 弹窗。scripts 分包(8.6MB)能正常加载证明分包机制本身可用，是 multTextures 这个包单独出问题。
- **修复（构建产物层，源码零改动）**：multTextures 分包改**远程 bundle**（走 8080 HTTP，与 resources 同路）：
  - `settings.b2b0e.json`：`engine.subpackages` 留 scripts，`engine.remoteBundles` = `["resources","multTextures"]`
  - `game.json`：subpackages 只留 scripts
  - `remote\multTextures\{config.0c4d2.json, import/01/017586550.7f3d8.json}` + `src\bundle-scripts\multTextures\index.0c4d2.js`
  - 依赖 engine-adapter.js 加载链：远程 bundle 命中 `remoteBundles` → `{server}remote/{name}/` + require `src/bundle-scripts/{name}/index.{ver}.js`
- **验证坑**：排查时曾误判「改造丢失」——settings.b2b0e.json 顶层读不到键，实际键嵌套在 `engine` 段下。
- **附带发现**：200MB 缓存配额满是独立坑（`copyfile:fail` 铁证），需定期清 DevTools 缓存。

## 4. 卡点③：网页端被搞坏 `webAsset import render failed`（10-26）

- **现象**：修复卡点②的过程中，网页预览（7456）开始报 `webAsset import render failed / reading 'make' / pushModeInStateInfo`，登录也挂。
- **弯路（已推翻的结论）**：全盘 16.7 万文件字符串扫描 + 18080 零记录 → 当时误判「DevTools 工具层报错，换 DevTools 版本」。**后被推翻**：这是 multTextures bundle 缺失的下游症状（渲染管线拿不到 Mult-material）。
- **根因**：`client\assets\multTextures.meta` 被写坏——SVN 基线 `isBundle:true`，工作副本变 `isBundle:false` + `compressionType:{"wechatgame":"subpackage"}`，mtime 10-23 18:51 正是构建时段（构建副作用）。meta 坏 → 编辑器不认 bundle → 预览 `/assets/multTextures/*` 404 → loadBundle 静默失败。同事干净 checkout 无此问题（对照实验定位）。
- **修复**：TortoiseSVN 还原该 meta（10-26 22:41 写回基线）→ 网页端恢复正常（用户确认）。
- **联动**：Version.ts 同日还原 `BUILD_VERSION` 占位符（构建写脏），网页登录链路全通。

## 5. 卡点④：微信端战斗仍崩 → 特权卡 cfg 快照缺卡（10-27 本轮对话）

本轮是「网页端已好、微信端战斗同之前报错」的收尾战，过程曲折，完整记录：

### 5.1 先排除设备/工具因素
用户问是否 DevTools / Cocos 版本问题 → 用户确认 **DevTools 已是最新版 2.02.2608080**，「换版本」方案作废；Cocos 3.7.3 与网页端一致，排除。

### 5.2 图2「报错」鉴别（伪报错教学）
用户截图刷屏的 `SF-RELEASE` / 裸 `Error` 堆栈 → 鉴定为 **gameDebug 构建的伪报错**：`[SF-RELEASE]`/`[SF-DECREF]` 是纹理释放调试日志，后者代码内 `(new Error).stack` 主动打印堆栈，Console 里呈现为裸 Error 帧，极易误读；`refUIs=[undefined×undefined]` 是日志 concat Map 展示缺陷。真错误藏在 Console 角标红色条目里。
（期间还纠偏了 OCR 误读函数名：`_onClickTogglerist`→`_onClickToggleList`、`完成释放`→`完成销毁`；以及 18080 抓不到分包报错的真因=`useIsolateContext:true` 分包隔离上下文，不是钩子没写对。）

### 5.3 抓到真实报错（图3）
```
TypeError: Cannot read properties of undefined (reading 'sys_id')            ×2 (dispatch err)
MiniProgramError: Cannot read properties of undefined (reading 'time_limit')
    at getPrivilegeVal ← responseBeforeFight                                  ← 致命
```
`responseBeforeFight` = 战斗前响应处理，特权卡取值崩了 → 战斗 UI 初始化中断 → 打不了战斗。

### 5.4 挖实现 + 核对配置
- 客户端 `PrivilegeMgr`（scripts 分包 game.js）：`onPrivilegeCardSync` 把服务端 `card_list` 原样全收进 `cardInfoMap`；`getCardCfg(e)=cfg_privilege_card[e]` **无任何容错**；`getPrivilegeVal` 直接读 `l.time_limit`。
- 客户端 assets 表与服务端 `cfg_privilege_card.lua` 当时核对均为 id 0~13 → 排除表错位。
- 服务端发卡入口全部校验 cfg，唯一不校验的是存档 `Load(mData)` → 当时推测「该账号脏存档」，**此猜想后被推翻**。

### 5.5 容错补丁（等授权 → 打补丁 → 一次成功）
写 `temp_case\scripts\priv_fix_patch.py`：三处容错（getPrivilegeVal / updateRedPoint / getPrivilegeCardStatus），查不到的卡 `console.warn("[PRIV-FIX] ... card_id=XX")` 后跳过，带唯一性命中断言 + 备份 `game.js.bak_privfix_20261027`。执行脚本因写 `E:\p1-x` 需禁沙箱+授权；用户回复「同意」后执行，三处均唯一命中，写盘成功（8.6MB，15:34）。

### 5.6 验证结果与根因定案（截图证据）
用户反馈 **战斗终于正常**，截图显示：
```
[PRIV-FIX] getPrivilegeVal skip card_id=13 entry={"card_id":13,"buy_time":0,"expire_time":0,"daily_reward_state":0}
```
异常卡是 **card_id=13（飞速推关特权卡），buy_time=0 未购卡** → 推翻「脏存档」猜想，真正的根因链：

1. 服务端配置 10-27 新增卡13（`cfg_privilege_card.lua` mtime 10-27 14:35，SVN 更新拉下来的）；
2. 用户 10-27 14:34 的 SVN 更新把 assets 客户端表同步到含卡13；
3. **微信构建产物里的 cfg 是 10-23 18:48 构建那一刻的快照，没有卡13**（铁证：产物内 grep `MainlineOneKeyCard`（卡13 node_name）零命中，而卡1 `FreeAdCard` 存在）；
4. 服务端 `SceneReady` 会给每个账号同步全部卡（含未购的 card_id=13，buy_time=0）→ 客户端查表 undefined → 崩；
5. 网页预览实时读 assets 最新表（有卡13）→ 一直正常。「网页正常/微信崩」的分叉点就是 **cfg 快照过期**，与账号无关。

补丁跳过的 buy_time=0 未购卡语义安全（未购卡不产生任何特权加成），属于正确兜底而非掩盖问题。

### 5.7 本轮的教训
- 微信端排查要**先看 Console 红条目**，别被 gameDebug 伪报错带偏；
- 构建产物 = 快照：**源码/配置在构建之后的任何更新，产物都不会自动跟上**（cfg、脚本都是）；
- 「只在一个端复现」≠ 账号数据问题，先对比两端读的数据源差异（assets 实时 vs 产物快照）。
