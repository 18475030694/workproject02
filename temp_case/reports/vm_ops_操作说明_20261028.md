```
D:\python\python3.9\python.exe -m pip install paramiko
```
装的是 **paramiko 5.1.0**（Python 的 SSH 库）。
> 为什么不用你想的"操作 SecureCRT 插件"：SecureCRT 脚本靠"等屏幕上出现某字符串"判断结果，超时难控、拿不到可靠退出码、还会动你的 GUI 会话。paramiko 直连 22 端口，输出/退出码全部可断言，且与你的 SecureCRT 互不干扰。**结论：SecureCRT 留给你人工用，自动化走 SSH 直连。**

## 4. 关键发现（你可能没想到、但我处理了的）

1. **"五个服"不是五个部署**。3~7 服 = cross_x1 内部 ServerList 的 server_id 3~7，共用一套进程、一个库 `game_cross_x1`。所以 `--server 5服` 和 `--server 3服` 是同一件事（工具照单全收，落在台账里好对账）。
2. **游戏进程是 root 跑的，而你 SSH 是 yang**。直接跑 `kill_all.sh` 会 Permission denied。工具已自动 sudo。
3. **`stop_all.sh` 有个隐藏坑**：它的优雅停服是 `curl 127.0.0.1:6011/index/stop_server`；**如果 directorsvr 已经死了，它会直接 `killall skynet`**——全机所有 skynet 一起死。目前一台机就一个部署所以无差别，但要知道有这个行为。
4. **`kill_all.sh` 永远是全机 kill -9**，无任何确认。工具给它加了 `--yes` 门槛 + 操作前自动 status 留证。
5. **`start_all.sh` 拒绝在有 skynet 存活时启动**（前置 baklog 检查到进程就 exit 1）。工具在 start 前先做预检，直接告诉你"先 stop"。
6. **`config/` 是单份共享的**：每次 `start_all.sh <env>` 都会 `rm -rf config/` 重新生成——谁最后 start，config 就是谁的。当前机器只有一个 cross_x1 在用，无影响；以后若加多 env 记得这一点。
7. **备份/还原不依赖当前 config 是哪个 env**：mongos.conf 的 host/port/user 恒定（127.0.0.1），库名由命令行参数拼（`game_<env>`），所以随时可以备份。
8. **备份是目录不是 tar.gz**：脚本里 tar 打包那行被注释了，"自动清理 14 天前备份"只删 `*.tar.gz`（等于永远删不到），**旧备份会无限堆积**。6 月以来的备份都在，磁盘 54G/98G 还够，但建议偶尔手动清老的。
9. **`mongo_recover.sh` 和 `recover_mongo.sh` 是两份一模一样的脚本**（重复品），用哪个都一样。还原是 `mongorestore --drop`：**先清空再灌入，覆盖式**；还原内容里没有的集合不会被清（脚本注释原话）。工具的 recover 子命令会**先自动备份当前库再还原**，双保险。
10. **VM 服务器时钟是全局时间源**：skynet、MongoDB、日志的时钟全部取自 VM OS 时钟，`date` 系统指令改它一处全局生效，覆盖面比 GM set_timeshift 完整（后者只动 skynet 层）。此前时钟停在 2026-10-16（上次手动调时间未拨回的遗留），**2026-10-28 已用 `setdate --sync-local` 拨回真实时间**。新备份目录名、日志时间戳都会跟着当前时钟走，见 §7.2。
11. **trunk 比 VM 旧**：VM 的 env_config 有 `cross_x1.lua`，本地 trunk 没有——以后别拿 trunk 的 env_config 目录判断合法 env。
12. **备份列表按 mtime 排序**：`game_cross_x1_2026-10-23-10-03-03` 排在最前是因为它 mtime 最新（可能被复制/touch 过），不是按名字排的。认目录名里的时间戳更稳。
13. **防呆三件套**：高危命令必须 `--yes`；服名走白名单（乱敲直接报错并列出可用名）；每次操作写台账（`vm_ops_ledger.jsonl`），出事可溯源。
14. **本地/远端脚本一致性校验**：md5 对过，start_all.sh、service_ctrl.sh 两边一致——工具注释里写的行为就是线上真实行为。

### 7.1 停服→备份→回档→开服 闭环实录（2026-10-28）

1. `stop --yes`：GM 优雅停服返回 OK，**进程异步退出**（约 8s 后 ps 计数归零）。注意 `status` 显示的 PID 是 config 文件里的记录值，停服瞬间可能仍显示旧值，真实存活以 `ps -ef | grep skynet` 为准（工具内部的 skynet_running 检查就是用 ps，可靠）。
2. `backup`：当前库全量备份 `game_cross_x1_2026-10-16-20-46-38`（约 90 集合，role/account 各 41 条，1.8s）。时间戳取自 VM 时钟（落后真实 12 天），不影响使用。
3. `recover --dir game_cross_x1_2026-10-16-20-27-30 --yes`：先自动备份当前库（`20-47-23`，第二道保险），再 `mongorestore --drop` 覆盖还原——3271 documents restored / 0 failed，索引全部重建，3.9s。
4. 清除本次两份当前库备份（rm -rf 精确全路径，备份目录恢复为原 12 份）。
5. `start`：rm old configs → gen configs（zonesvr_num=6 等打印）→ 14 进程按序拉起；终检 skynet 计数 14、`db.role.countDocuments()`=41 与还原源一致。

### 7.2 调时间→跨 0 点→拨回 闭环实录（2026-10-28，setdate 子命令）

背景：开功能/活动、收活动、赛事跨服等场景需要服务器"跨日"。VM OS 时钟是 skynet/MongoDB/日志的统一时间源，用系统指令 `date 月日时分年` 改它一处全局生效，比 GM set_timeshift 更完整可信。

1. **防呆验证（开服状态）**：`setdate --datetime "2026-10-29 23:58" --yes` → 工具检测到 14 个 skynet 存活，**拒绝执行**（exit 1，时间未动），提示先 stop。✅
2. `stop --server cross_x1 --yes` → 约 8s 后 ps 计数归零。
3. `setdate --datetime "2026-10-29 23:58" --yes`：改前 2026-10-16 21:56:36 → **2026-10-29 23:58:00**（改前/改后均回显）。✅
4. `start --server cross_x1`：14 进程拉起；`log/baklog/20261029_235809/` 目录名直接取自新时钟，证明开服动作跑在新时间下。
5. **自然跨 0 点**：约 2 分钟后 `date`=2026-10-30 00:00:06，14 进程全存活；`log/scenesvr1.error` 在 `[2026-10-30 00:00:00]` 打出 `==WeekDay 5 Hour 0 share_res NewHour====`——整点/每日调度按新日期触发，WeekDay 5（周五）与 10-30 吻合。✅
6. 回程：`stop --yes` → `setdate --sync-local --yes`（目标=本机真实时间 2026-10-28 17:38）→ `start` → 终检 14 进程、VM 时间=真实时间。✅
7. 台账：`vm_ops_ledger.jsonl` 记录 setdate 三步（查时/设置/校验），密码自动掩码。

注意事项（写入使用教程 §6）：
- setdate 须在**关服窗口**执行（工具强制）；改完开服等自然跨 0 点即触发每日重置。
- VM **硬件时钟未同步**（hwclock 无写入），虚拟机重启后时间可能还原，重启用 vm_ctl 流程后注意核对 `date`。
- 改 VM 时间后，GM set_timeshift 的偏移模型失效，需重新实测校准。
- 向前跳转后尽量避免往回调（按未来日期开启的活动可能错乱）；测试 VM 上短暂跳转+拨回已实测无恙。

## 8. 回滚方式

- 工具/配置/文档/台账全是**新增文件**，删掉即回滚，VM 侧零改动（setdate 改的系统时间已用 `--sync-local` 拨回真实时间）。
- 2026-10-28 闭环验证在 VM 上的"写"动作均已还原：数据库已回到还原源状态并开服，本次临时备份已删除，VM 上无遗留。
