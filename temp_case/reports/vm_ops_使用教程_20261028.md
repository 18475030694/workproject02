## 2. 命令速查（复制即用）

统一在 `E:\workproject` 下执行；`python` = `D:\python\python3.9\python.exe`。

```bash
:: 查状态（安全，随时可敲）
python temp_case\scripts\vm_ctl.py status

:: 开服（约 10~60 秒）
python temp_case\scripts\vm_ctl.py start --server 5服

:: 正常关服（高危，必须 --yes）
python temp_case\scripts\vm_ctl.py stop --server 5服 --yes

:: 强杀全部 skynet（最暴力，卡死才用）
python temp_case\scripts\vm_ctl.py kill --server 5服 --yes

:: 备份数据库（安全，3 秒左右）
python temp_case\scripts\vm_ctl.py backup --server 5服

:: 看有哪些备份可还原
python temp_case\scripts\vm_ctl.py backups --server 5服

:: 回档到某个备份（高危：先停服 → 工具自动备份当前库 → --drop 还原）
python temp_case\scripts\vm_ctl.py stop --server 5服 --yes
python temp_case\scripts\vm_ctl.py recover --server 5服 --dir game_cross_x1_2026-10-23-10-03-03 --yes
python temp_case\scripts\vm_ctl.py start --server 5服

:: 虚拟机电源层
python temp_case\scripts\vm_ctl.py vm list          :: 在运行的虚拟机
python temp_case\scripts\vm_ctl.py vm snap          :: 快照列表
python temp_case\scripts\vm_ctl.py vm on            :: 开机
python temp_case\scripts\vm_ctl.py vm off --yes     :: 关机（先 stop 关游戏服！）

:: 调 VM 系统时间（高危，必须关服窗口；跳开服天数/开活动跨 0 点用）
python temp_case\scripts\vm_ctl.py stop --server 5服 --yes
python temp_case\scripts\vm_ctl.py setdate --datetime "2026-10-30 23:58" --yes
python temp_case\scripts\vm_ctl.py start --server 5服
:: 测完拨回真实时间
python temp_case\scripts\vm_ctl.py stop --server 5服 --yes
python temp_case\scripts\vm_ctl.py setdate --sync-local --yes
python temp_case\scripts\vm_ctl.py start --server 5服

:: 探查 / 任意命令（自由扩展）
python temp_case\scripts\vm_ctl.py probe
python temp_case\scripts\vm_ctl.py raw --cmd "tail -50 log/error.err"
```

## 3. 每条命令会发生什么

| 命令 | 背后执行 | 预期表现 |
|---|---|---|
| `status` | `service_ctrl.sh status` | 列出 pid + config 文件名，14 个进程（含 zonesvr501~506）为正常 |
| `start` | 先预检"有无 skynet 存活"→ `start_all.sh cross_x1`（重建 config→按序拉起 9 类进程）→ 再查一次状态 | 若有进程存活会**直接拒绝**并提示先 stop |
| `stop` | 先 status 留证 → `stop_all.sh`（GM 优雅停服）→ 再查状态 | 进程应全部消失；若 120 秒没退尽，工具会提示用 kill |
| `kill` | 先 status 留证 → `kill -9` 全机 skynet | 秒杀；可能丢未落库数据，仅限卡死 |
| `backup` | `mongo_backup.sh game cross_x1` 逐集合 mongodump | 打印每个集合的条数，最后 `backup success!!`；跳过 battle_record |
| `backups` | ls 备份目录 | 新→旧列出目录名，**认目录名里的时间戳**（排序按 mtime 不按名） |
| `recover` | ① 检查备份目录存在 ② 检查已停服（没停直接拒绝）③ **自动备份当前库** ④ `echo yes \| mongo_recover.sh` 覆盖还原 | 结束后需手动 `start` 开服 |
| `setdate` | ① 三选一解析目标时间（`--datetime` / `--raw` 10 位月日时分年 / `--sync-local` 同步本机）② 回显改前时间 ③ **预检 skynet 存活即拒绝** ④ `sudo date 月日时分年` 改 VM OS 时钟 ⑤ 回显改后时间 | skynet/MongoDB/日志时钟全部跟着走；**必须关服窗口**，测完用 `--sync-local` 拨回 |
| `vm on/off` | vmrun start/stop（off 是 soft 优雅关机） | off 前务必先 stop 游戏服，防 mongo 硬断 |

## 4. 安全机制（为什么有些命令要 --yes）

1. **高危门槛**：stop / kill / recover / vm off / setdate 不加 `--yes` 直接拒绝执行。
2. **白名单**：`--server` 只认 `cross_x1` 和 `3服~7服` 别名，敲错立即报错并列出可用名——不会把命令打到你不知道的服务器上。
3. **操作留证**：stop/kill 前自动跑一次 status，前后对比写进台账。
4. **台账**：`temp_case/reports/vm_ops_ledger.jsonl`，每次操作一条（时间/命令/退出码/耗时/输出尾部，密码自动打码）。出问题翻这里对账。

## 5. 四个典型工作流

### A. 例行备份（最常用，一条命令）
```
python temp_case\scripts\vm_ctl.py backup --server 5服
```

### B. 改坏数据回档
```
:: 1) 停服
python temp_case\scripts\vm_ctl.py stop --server 5服 --yes
:: 2) 挑备份
python temp_case\scripts\vm_ctl.py backups --server 5服
:: 3) 回档（自动先备份当前库）
python temp_case\scripts\vm_ctl.py recover --server 5服 --dir game_cross_x1_2026-10-23-10-03-03 --yes
:: 4) 开服
python temp_case\scripts\vm_ctl.py start --server 5服
```

### C. 虚拟机重启后全套拉起
```
python temp_case\scripts\vm_ctl.py vm list      :: 确认 VM 在跑（不在则 vm on）
python temp_case\scripts\vm_ctl.py status       :: 确认游戏服没起
python temp_case\scripts\vm_ctl.py start --server 5服
```

### D. 跳开服天数 / 开活动跨 0 点（2026-10-28 实测闭环 PASS）
原理：VM OS 时钟是 skynet/MongoDB/日志的统一时间源，关服窗口用 `date` 改它全局生效；开服后等自然跨 0 点，服务端整点/每日调度自动触发。
```
:: 1) 停服
python temp_case\scripts\vm_ctl.py stop --server 5服 --yes
:: 2) 调到目标日前一晚 23:58（例：跳到 10-30，就设 10-29 23:58）
python temp_case\scripts\vm_ctl.py setdate --datetime "2026-10-29 23:58" --yes
:: 3) 开服，等约 2 分钟自然跨 0 点（期间可上号看每日重置）
python temp_case\scripts\vm_ctl.py start --server 5服
:: 4) 测完：停服 → 拨回真实时间 → 开服
python temp_case\scripts\vm_ctl.py stop --server 5服 --yes
python temp_case\scripts\vm_ctl.py setdate --sync-local --yes
python temp_case\scripts\vm_ctl.py start --server 5服
```
实测证据：跨 0 点时 14 进程全存活，`log/scenesvr1.error` 打出 `[2026-10-30 00:00:00] ==WeekDay 5 Hour 0 NewHour====`（星期与目标日吻合）。

## 6. 故障排查

| 现象 | 原因/处理 |
|---|---|
| `SSH执行异常: ...` | VM 没开机（`vm list` 看下）或 IP 变了（改 json） |
| start 报"skynet 正在运行" | 先 `stop --yes` 再 start（start_all 的 baklog 前置检查，属脚本原生行为） |
| stop 后还有残留进程 | 上 `kill --yes` |
| stop 返回 OK 但 status 还显示一堆 PID | 正常：优雅停服是**异步**的，进程要几秒才退尽；且 status 显示的是 config 里记录的 PID，不代表活着。等 10 秒后用 `raw --cmd "ps -ef | grep skynet | grep -v grep | wc -l"` 看真实数量（0=全停） |
| 备份报"配置文件 ... 不存在" | config/ 被清了没重建；先 `start` 一次（start_all 会重新生成 config）再备份 |
| 回档报"目录不存在" | 目录名抄错；用 `backups` 查，目录名**不含末尾斜杠** |
| 显示的时间不对（如 10-16） | VM 时钟被调过没拨回。开服中就先 `stop --yes`，再 `setdate --sync-local --yes` 拨回真实时间，然后 `start` |

## 7. 注意事项

1. 3~7 服**共库共进程**：备份/开关服都是对整个 cross_x1 部署生效，不是只动"5 服"。
2. 备份是目录、**不会自动清理**（脚本的 14 天清理只删 tar.gz，而 tar 从不生成）——偶尔手动清旧备份，磁盘目前 39G 可用。
3. `mongo_recover.sh` 与 `recover_mongo.sh` 是重复脚本，效果一样。
4. 本工具与 SecureCRT 可以并存：工具走 SSH 独立会话，不影响你人工登录；但**同一时间别一边 stop 一边人工 start**，先看 status。
5. `vm_servers.local.json` 含明文密码，只在本机与 workproject01 备份仓存在，**不要提交到公开仓（workproject02）**。
6. setdate 四条硬约束：①必须关服窗口执行（工具检测到 skynet 存活直接拒绝）；②VM 硬件时钟未同步，**虚拟机重启后时间可能还原**，重启后记得核对 `raw --cmd "date"`；③改 VM 时间后 GM set_timeshift 的偏移模型失效，需重新实测校准；④向前跳转后尽量避免往回调（按未来日期开启的活动可能错乱），测完及时 `--sync-local` 拨回。
